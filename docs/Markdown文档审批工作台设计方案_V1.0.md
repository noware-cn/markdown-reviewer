# Markdown 文档审批工作台：产品与界面设计方案

版本：V1.0
日期：2026-11-06
状态：设计基线已确认，待进入开发

## 1. 文档目的

本文档固化 Markdown 文档审批工作台的产品定位、交互设计、视觉规范、技术实现约束、实施范围和验收标准，作为后续开发会话的唯一设计基线。

本方案由用户于 2026-11-06 明确确认。后续开发应先读取本文档及仓库现状，不应仅凭聊天摘要实施；如实现中发现设计与当前代码或 GitHub API 能力冲突，应先记录差异和影响，再提出必要决策，不得静默改变产品方向。

## 2. 产品定位与核心原则

### 2.1 产品定位

产品定位为**个人 Markdown 文档审批工作台（Personal Markdown Review Workbench）**。它面向 GitHub Pull Request 中的 Markdown 文档变更，重点服务架构设计、技术方案、项目治理和技术研究等长篇中文技术文档的阅读、差异核对、批注和审批。

产品不是通用代码评审系统，不是 Markdown 编辑器，也不是团队协作平台。

| 维度 | 定位 |
|---|---|
| 核心对象 | GitHub PR 中变更的 Markdown 文档 |
| 核心任务 | 阅读、理解、核对、批注、审批 |
| 使用方式 | 个人单用户使用 |
| 内容来源 | GitHub PR 的 Base / Head 版本 |
| 内容展示 | 完整 Markdown 文档及准确差异 |
| 意见管理 | 行级评论、整体 Review |
| 审批结果 | Approve、Request changes、Comment |
| 本地状态 | 草稿、个人审阅进度和阅读位置 |

### 2.2 设计原则

1. **文档优先：** 文档正文占据主要视觉与空间资源。
2. **阅读连续：** 查看差异、评论和文件时尽量不切换页面、不丢失阅读位置。
3. **差异准确：** 新增、删除、修改均可追溯到源文件及准确行号。
4. **信息渐进：** 默认只展示必要信息，细节按需展开。
5. **操作克制：** 审批操作明确，但不干扰长时间阅读。
6. **结构稳定：** 文件、模式、意见面板切换不应造成页面大幅跳动。
7. **轻量单人：** 不建设多人协作、团队管理、角色权限矩阵、并发审批、实时协同、团队报表和复杂通知。

## 4. 信息架构

应用分为两个主要界面：

### 4.1 审批任务列表

仅承担任务入口，不应在进入工作台后继续占据空间。展示 PR 标题、编号、仓库、作者、更新时间、变更文件数、新增/删除行数、审批状态及本地草稿提示。

进入 PR 后切换到全窗口工作台。返回列表时尽量恢复列表位置和筛选条件。

### 4.2 文档审批工作台

由以下区域构成：

- 顶部任务栏：返回、PR 标题/状态、变更统计、阅读模式、搜索、意见入口和 Review 操作。
- 左侧导航：变更文件列表、文件状态、增删行数、待处理意见数、Markdown 章节树。
- 中央阅读区：完整文档、差异标记、阅读控制和定位。
- 右侧意见抽屉：默认收起，展示当前文件评论、本地草稿和历史意见。
- 不设置常驻底部工具栏，避免挤占垂直阅读空间。

## 5. 工作台布局规范

### 5.1 桌面端结构

采用左侧可折叠导航 + 中央自适应阅读区的基础布局；意见面板展开时才形成第三列。不得沿用多个固定侧栏叠加挤压正文的布局。

建议尺寸：

| 区域 | 推荐尺寸 | 行为 |
|---|---:|---|
| 顶部任务栏 | 56–64px | 固定 |
| 左侧文件导航 | 220–248px | 可折叠 |
| 右侧意见面板 | 320–380px | 默认收起 |
| 正文最大宽度 | 约 1120px | 可调 |
| 正文左右留白 | 48–72px | 随窗口变化 |

文档阅读区域宽度不等于正文最大宽度。超宽屏仍应保留舒适行长；表格和代码块可突破正文宽度。

布局建议：

~~~css
.workbench {
  display: grid;
  grid-template-columns: var(--navigation-width) minmax(0, 1fr);
  height: 100dvh;
}

.workbench.review-open {
  grid-template-columns:
    var(--navigation-width)
    minmax(0, 1fr)
    var(--review-width);
}

.document-reading {
  min-width: 0;
  overflow: auto;
}

.document-content {
  width: min(100% - 96px, 1120px);
  margin-inline: auto;
}
~~~

当窗口不足以容纳可读正文宽度时，右侧意见面板转为覆盖式抽屉；不得持续压缩正文。左侧导航也应允许收起。

### 5.2 响应式要求

- 1920×1080：意见面板收起时正文周围有充分留白，阅读区域充分利用屏幕。
- 1440×900：不出现固定三栏挤压，正文保持可读。
- 窄窗口：优先收起左侧导航；意见面板改覆盖式抽屉。
- 面板展开和收起不得导致文档滚动位置丢失。

## 6. 三种阅读模式

三种模式必须共用同一套差异数据模型，确保变化结果一致。

### 6.1 阅读改动（默认模式）

以 PR Head 修改后的完整 Markdown 文档为主体，在原有上下文中嵌入差异标记。它不是只把新增行染色，而是让审批者阅读完整、连贯的最终文档，并理解变化。

| 变更类型 | 展示方式 |
|---|---|
| 未修改内容 | 正常 Markdown 排版 |
| 新增段落 | 原位置完整显示，浅绿色背景或左侧标记 |
| 删除段落 | 在对应上下文位置插入删除内容块，浅红色背景 |
| 修改段落 | 新内容正常显示，关联旧内容作为删除块 |
| 纯格式变化 | 轻量提示，可按需查看源码 |
| 移动/重命名 | 显示位置变化或文件状态提示 |

交互要求：

- 点击变更标记可展开/收起旧内容。
- 点击变更编号可定位源码 Diff。
- 段落或变更块提供添加评论入口。
- 章节导航定位到完整文档中的对应章节。
- 文件切换默认进入阅读改动模式。
- 提供“显示变更标记”开关；关闭后纯粹阅读修改后的文档。
- 不得因关闭标记而丢失差异数据或评论锚点。

删除内容在 Head 版本中不存在，必须插入可理解的删除块。优先使用相邻新增块或未修改上下文作为锚点，其次使用旧版本章节位置。无法可靠映射时显示独立的“删除内容”块，并提供源码 Diff 跳转；不得丢弃删除内容或制造错误定位。

### 6.2 前后对照

- 左侧展示 PR Base 完整文档，右侧展示 PR Head 完整文档。
- 两侧滚动同步，支持关闭同步独立浏览。
- 章节和对应段落尽可能建立关联。
- 点击一侧变更时，另一侧定位到对应内容。
- 无变化内容仍完整展示。
- 差异高亮、源码行号和评论定位保持可用。

不采用简单逐行滚动同步。应以章节、块级节点和差异锚点为基础定位，避免段落高度、表格和代码块不同造成错位。

### 6.3 源码 Diff

保留两种精确核对视图：

1. 统一 Diff：紧凑查看变更序列。
2. 分栏 Diff：逐行核对旧、新源码。

保留文件路径、旧/新行号、新增/删除行、GitHub 行级评论锚点；支持折叠未变化上下文、展开更多上下文、上一处/下一处变更。

不再将“渲染对比”作为与源码 Diff 并列的独立模式。完整文档渲染能力整合进“阅读改动”和“前后对照”。

## 7. Markdown 阅读体验规范

整体采用偏技术出版物的编辑式极简风格，而非传统管理后台。

### 7.1 排版基线

| 元素 | 建议规格 |
|---|---|
| 正文字号 | 16px |
| 正文行高 | 1.85 |
| H1 | 30px / 1.4 |
| H2 | 24px / 1.5 |
| H3 | 20px / 1.55 |
| H4 | 17px / 1.6 |
| 段落间距 | 14–18px |
| 列表行距 | 1.75 |
| 表格字号 | 14px |
| 代码字号 | 13–14px |
| 正文最大宽度 | 约 1120px |

中文正文字体栈：

~~~css
font-family:
  -apple-system,
  BlinkMacSystemFont,
  "Segoe UI",
  "PingFang SC",
  "Microsoft YaHei",
  sans-serif;
~~~

代码区域采用独立等宽字体栈，如 Cascadia Code、JetBrains Mono、Consolas、monospace。

### 7.2 内容元素

- 标题层级清晰，H1–H4 有明确字号、字重和留白层次。
- 表格区分表头，长文本自动换行，长表格横向滚动；差异可定位到具体单元格。
- 代码块支持语法高亮、语言标签、一键复制、横向滚动；必要时显示行号和差异。
- 引用块采用低对比度背景和左侧强调线。
- 图片按可用宽度自适应、保持比例，支持查看大图和加载失败占位。
- 链接有明确视觉区分和打开行为。
- 任务清单、嵌套列表、水平线等均应正确呈现。
- 任意 HTML 必须经过安全处理，不允许脚本执行。

### 7.3 Markdown 解析

不继续扩展自定义 Markdown 解析器。采用成熟解析器及扩展机制，至少覆盖 CommonMark、GFM 表格、删除线、任务清单、自动链接、代码围栏、多级标题、引用、图片；数学公式按实际文档需求启用。配合语法高亮和 HTML 安全清洗。

解析器选型应先检查项目当前依赖、Worker 静态资源和浏览器兼容性，再决定具体库；不得无依据引入大型依赖。

## 8. 文件、章节和变更导航

### 8.1 文件导航

每个文件展示路径/文件名、增加/修改/删除状态、增删行数、待处理变更数量和未提交意见状态。

默认按 GitHub 文件顺序排列，避免审阅状态变化导致列表跳动；可提供“待处理优先”排序，但切换必须由用户主动触发。

### 8.2 章节导航

选中文件后显示 Markdown 标题树。支持点击定位、当前章节高亮、滚动联动、子章节折叠；变更章节显示轻量标记，有意见的章节显示数量。

### 8.3 变更导航

提供上一处/下一处变更。跳转以完整文档为定位对象，滚动到变化段落并短暂高亮；不改变阅读模式，不强制打开意见抽屉。

### 8.4 个人审阅进度

轻量保存文件访问/审阅状态、当前文件、章节或滚动位置、未提交意见草稿。个人“已审阅”状态必须与 GitHub Review 的批准状态区分。

## 9. 评审批注和审批操作

### 9.1 意见抽屉

右侧面板默认收起。展开后展示当前文件意见、GitHub Review 评论、本地草稿、状态、源码行号和所属章节上下文。

可提供全部、未解决、已解决、我的草稿等轻量筛选，不建设独立复杂意见管理中心。

### 9.2 行级评论

- 段落 Hover 时出现评论入口；变更块也可直接添加意见。
- 点击后建立源码行号锚点并打开编辑器。
- 短意见采用行内编辑或轻量浮层；长意见使用右侧面板。
- 自动保存本地草稿。
- 明确区分“本地草稿”和“已提交评论”。
- 表格、代码块、引用块支持块级锚点；最终仍映射到 GitHub 支持的文件行号/行范围。
- 锚点不能可靠映射时禁止生成评论锚点，明确提示用户改用源码 Diff 定位。

### 9.3 评论映射

渲染 DOM 必须保留 Markdown 源码行号信息，例如：

~~~html
<p data-source-line="24">...</p>
~~~

复杂块还需记录起止行、旧版本行号、新版本行号和差异块 ID。不能通过渲染后 DOM 位置反推源码行号。

GitHub Review API 的评论锚点通常要求 PR Diff 中的行和 side/position 等信息。实现时必须核对现有 Worker 接口和 GitHub API 参数，不得把 Markdown 源码行号直接等同于 Diff position。

### 9.4 整体 Review

保留 Approve、Request changes、Comment 三种结果。提交前展示 Review 类型、待提交意见数量、整体评论和当前 PR 最新 Head SHA。提交成功后刷新状态；失败时保留所有草稿。

PR 更新后，旧草稿绑定的 Head SHA 若已过期，应提示重新定位，禁止将评论静默提交到错误版本。锚点失效时保留评论内容并明确提示。

## 10. 顶部工具栏与阅读控制

顶部只保留高频操作：

- 返回任务列表；
- PR 标题、状态和变更统计；
- 阅读模式切换；
- 章节导航入口；
- 当前文档搜索；
- 意见抽屉入口；
- Review 提交入口。

低频操作放入更多菜单：刷新 PR 数据、打开 GitHub 原始 PR、查看提交记录、切换显示密度、显示/隐藏变更标记。

阅读控制建议包括正文宽度（舒适/宽屏）、字号（小/标准/大）、变更标记显示开关、章节导航显示开关，以及“仅查看有变更内容”筛选。后者不是默认模式，必须保留足够上下文。

## 11. 视觉设计语言

采用 Editorial Minimalism + Technical Workbench：

- 大面积中性背景、白色正文区域、清晰文字层次。
- 克制边框、低对比分隔、充分留白。
- 新增采用柔和绿色，删除采用柔和红色，修改/定位采用低饱和蓝色或琥珀色。
- 差异状态不能仅依赖颜色，必须配合文字标签、图标或边框。
- Hover 和定位动效轻量，不使用大面积动画。
- 支持清晰键盘焦点状态。
- 浅色模式优先完成；深色模式后续实现，必须重新校准正文、代码、表格和差异对比度，不能简单反色。

## 12. 技术实现基线

### 12.1 分层职责

1. 工作台 UI 层：布局、导航、阅读模式、意见面板、审批操作。
2. Markdown 呈现层：解析、语法高亮、排版、安全清洗、DOM 源码锚点。
3. 差异计算与映射层：源码 Diff、块级结构映射、行号映射和变更标注。
4. 审批业务层：PR 数据、评论、草稿、Review 状态和个人审阅进度。
5. Worker / GitHub API：现有数据接口、权限和审批提交链路。

### 12.2 统一差异模型

不直接以 GitHub Diff 字符串作为全部阅读视图的数据源。应建立内部统一差异模型，示意如下：

~~~ts
interface DocumentChange {
  id: string;
  type: "added" | "deleted" | "modified" | "moved";
  oldRange?: { startLine: number; endLine: number };
  newRange?: { startLine: number; endLine: number };
  oldContent?: string;
  newContent?: string;
  sectionPath?: string[];
  blockType?: string;
}
~~~

具体类型应结合现有代码、GitHub patch 和解析器能力调整，不要求机械照搬示例。

三种模式共享该模型：
- 阅读改动：映射到 Head 文档 DOM。
- 前后对照：分别映射到 Base、Head 文档 DOM。
- 源码 Diff：展示原始行级差异。

### 12.3 两层差异处理

**源码差异层：** 以 GitHub Diff 或标准文本 Diff 算法为基础，保留旧、新行号，识别新增、删除、修改、移动及文件新增/删除/重命名。

**文档结构层：** 解析 Markdown AST，识别标题、段落、列表、表格、代码块等结构节点，将源码差异映射到文档块。不能只凭标题文本匹配章节；须考虑标题重命名、章节移动和重复标题。

无法可靠映射时宁可明确提示并回退源码 Diff，不得错误映射或丢弃变化。

### 12.4 性能和状态

- PR 数据按需加载。
- Markdown 解析结果缓存，文件切换避免重复解析。
- 大文件可评估分段渲染。
- 差异定位使用稳定块级 ID。
- 草稿、当前文件、章节和滚动位置本地持久化。
- 不要过早引入虚拟滚动；长文档阅读连续性优先。只有实测性能不足时才评估虚拟化，并验证其不破坏定位、选区和评论锚点。

## 13. 异常和边界场景

| 场景 | 预期行为 |
|---|---|
| 新增文件 | 完整新文档，全部内容标记新增 |
| 删除文件 | 展示旧文档和删除状态，允许阅读旧内容 |
| 文件重命名 | 关联旧路径和新路径 |
| 章节整体移动 | 尽量识别移动，避免全部误判为删除/新增 |
| 标题重命名 | 关联前后章节并展示变化 |
| 大段落重写 | 关联旧、新段落 |
| 表格修改 | 定位变化单元格 |
| 代码块修改 | 定位变化行及上下文 |
| 删除末尾章节 | 在正确章节位置展示删除块 |
| 纯空格/格式变化 | 轻量提示，避免噪声 |
| 无法映射差异 | 明确提示并可跳转源码 Diff |
| PR 更新 | 检查 Head SHA 变化，提示草稿过期 |
| 评论锚点失效 | 保留评论内容，不静默迁移锚点 |
| 评论提交失败 | 草稿不丢失 |

## 14. 实施阶段与优先级

### P0：核心阅读体验重构

- 全窗口工作台布局。
- 文件导航可折叠，意见面板抽屉化。
- 阅读改动模式。
- 新增、删除、修改内容完整展示。
- 旧、新源码行号映射。
- 三种模式共用差异模型。
- 基础章节导航。

验收目标：能在完整文档中准确阅读所有变更，而不是依赖传统 Git Diff 阅读文档。

### P1：Markdown 阅读体验升级

- 成熟 Markdown 解析器。
- 完整排版体系。
- 表格、代码块、引用和列表优化。
- 语法高亮、图片和链接。
- HTML 安全清洗。
- 差异标记视觉优化。
- 前后对照模式。
- 阅读位置保持。

验收目标：长篇中文技术方案达到专业文档阅读器的体验水平。

### P2：审批交互完善

- 行级评论。
- 意见抽屉。
- 本地草稿。
- 文件审阅状态。
- Review 提交确认。
- 意见与源码行号映射。
- GitHub Review 提交链路回归。

验收目标：完成阅读、批注到提交 Review 的完整流程。

### P3：体验打磨

- 章节变更导航。
- 上一处/下一处变更。
- 文档搜索。
- 字体大小和正文宽度调节。
- 深色模式。
- 键盘快捷键。
- 阅读进度恢复。

验收目标：提升日常效率和长时间阅读舒适度。

## 15. 验收标准

### 15.1 阅读体验

- 默认正文字号 16px、行高约 1.85。
- 正文最大宽度约 1120px。
- 1920×1080 下正文周围有充分留白。
- 1440×900 下不被固定三栏挤压。
- 章节定位准确，当前章节随滚动同步。
- 切换模式、文件、意见面板不丢失阅读位置。
- 表格和代码块不发生布局溢出或内容裁切。

### 15.2 差异准确性

- 新增内容不能遗漏。
- 删除内容不能遗漏。
- 修改内容能够关联旧、新版本。
- 章节移动不能简单误判为全部删除和新增。
- 源码行号准确。
- 无法映射的差异必须可见。
- 三种阅读模式的变更结果一致。

### 15.3 审批功能

- 行级评论准确提交到 GitHub。
- 草稿刷新后可恢复。
- Review 类型正确。
- 评论数量和提交状态准确。
- 提交失败不丢失草稿。
- PR 更新后能识别旧版本锚点失效。

### 15.4 兼容性与性能

- Windows 桌面浏览器正常使用。
- 1440px、1920px 常见桌面分辨率正常。
- 小窗口时面板合理收起。
- 大型 Markdown 文档加载有明确反馈。
- 无明显重复渲染和滚动卡顿。
- 控制台无未处理异常。

## 16. 本次明确不做

- 多用户体系、团队管理、角色权限矩阵。
- 实时协同审批、并发冲突处理。
- 审批工作流配置。
- 团队统计报表和复杂通知中心。
- 独立 Markdown 编辑器。
- 自建 Git 版本管理。
- 复杂意见管理中心。

现有 Worker 登录、OAuth、数据读取和写入权限机制暂作为既有系统能力保留。本文“不建设多人协作/权限体系”是产品范围约束，不代表本次应擅自删除现有认证链路。任何认证或后端接口改动须有独立理由和回归验证。

## 17. 开发实施约束

1. **先验证差异模型，再全面开发界面。** 使用真实 PR 文档覆盖段落重写、章节移动、表格修改、代码块修改和大段删除，先证明差异能够正确映射。
2. **保护现有审批链路。** GitHub PR 获取、评论提交、草稿保存和 Review 提交属于回归保护范围，不因前端重构随意改变。
3. **分阶段实施。** 优先 P0，完成后再推进 P1/P2/P3，避免一次性无边界重构。
4. **浏览器实测。** 至少检查 1440×900 和 1920×1080 的布局、滚动、差异定位和评论交互。
5. **控制依赖。** 先盘点当前依赖和 Worker 部署限制，再选择 Markdown 解析、安全清洗和语法高亮库。
6. **不擅自改变设计决策。** 影响默认阅读模式、差异语义、评论锚点、审批链路或实施范围的变化，先提交决策供用户确认。
7. **不部署，除非用户明确要求。** 本轮仅保存设计方案，不进行代码修改、生产部署或 PR 合并。
8. **遵守仓库 AGENTS.md。** 所有工作在主题分支完成；不得将任何改动合并到 main，合并必须由用户本人在 GitHub 网页端完成。
