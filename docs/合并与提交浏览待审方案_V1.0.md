# 合并与 PR 提交浏览 待审方案 V1.0

- 状态：已实施（2026-11-10，见 README「按提交浏览与合并」）
- 日期：2026-11-10
- 适用代码：`markdown-reviewer`（Cloudflare Worker + 原生前端）
- 关联文档：`docs/Markdown文档审批工作台设计方案_V1.0.md`

## 1. 目标

在现有「PR 阅读 / 行级评审批注」工作台上增加两项能力：

1. **合并**：在工作台内直接合并 PR，合并前完成权限、可合并状态、head 版本校验，合并后立即切换到只读状态。
2. **PR 提交浏览**：列出 PR 内的每次提交，按提交查看该次提交自己的 diff，复用现有四种阅读视图（阅读改动 / 前后对照 / 统一 Diff / 分栏 Diff）。

两项能力相互独立，可以分两期上线；但合并方式会影响提交历史是否保留，需要在方案中一并明确。

## 2. 非目标

本期不做：

- 评论 → 提交的自动映射（“哪条已解决评论对应哪次提交”的推断）。
- 在历史提交上新增行级评论。
- GitHub auto-merge（自动合并队列的开启/关闭）。
- 合并方式之外的提交说明模板、提交信息规范校验。
- 列表页行内快捷合并（缓存状态容易误合）。
- 提交累计区间视图（`base...commit`）。

## 3. 现状与可复用点

| 现有能力 | 位置 | 复用方式 |
|---|---|---|

| 任意 ref 的文件正文 | `src/diff.ts:187 getFileText` | 直接传父提交 sha / 提交 sha |
| 审查评论 | `src/diff.ts:222 getReviewComments` | 补 `commitId` / `originalCommitId`，提交视图过滤 |
| 5 分钟取数缓存 | `src/index.ts:55 apiCache` | 扩 key，补容量上限 |
| Review 提交 | `src/index.ts:417` | 合并接口沿用同一套会话/错误处理模式 |
| 四种视图与行号锚点 | `public/diff-model.js`、`public/diff.js` | 只要喂对 base 正文 / head 正文 / patch，无需改渲染器 |

关键判断：**提交浏览不重写差异模型**。单提交视图等价于把 `buildModel(headText, baseText, patch)` 的输入换成「父提交正文、该提交正文、该提交 patch」。

## 4. 总体设计

### 4.1 数据流

```
打开 PR
  ├─ GET /api/approvals/{n}/diff            现有：meta + 全部改动 files + comments
  ├─ GET /api/approvals/{n}/commits         新增：提交列表（懒加载）
  └─ GET /api/approvals/{n}/merge-options   新增：合并权限、可用方式、可合并状态

选择某次提交
  ├─ GET /api/approvals/{n}/commits/{sha}           提交详情 + files（带 patch）
  └─ GET /api/approvals/{n}/commits/{sha}/file      提交时刻的 base/head 正文

合并
  └─ POST /api/approvals/{n}/merge            校验 + PUT GitHub merge + 失效缓存
```

### 4.2 视图状态

```js
D.rev = { kind: "all" } | { kind: "commit", sha, detail }
D.revKey = `all@${meta.headSha}` | `commit@${sha}`
D.all = { files, comments }          // 全部改动快照，切回时恢复
D.commits = { items, loaded, loading, error, stale }
D.commitDetails = new Map()          // sha -> detail
D.merge = { options, loading, error, done }
```

`D.meta` 始终是 PR 级元信息；`D.files`、`D.commentsByPath` 表示**当前视图**的数据。

## 5. 合并功能

### 5.1 GitHub 接口与约束

- 合并：`PUT /repos/{owner}/{repo}/pulls/{number}/merge`
  - body：`commit_title`、`commit_message`、`sha`、`merge_method`（`merge` / `squash` / `rebase`）
  - `sha` 用于锁定 head：与当前 head 不一致时 GitHub 返回 409，防止在旧视图上合入新提交。
- 权限：登录者对仓库需有 write / maintain / admin；组织成员身份不等于合并权限。
- 仓库设置决定可用方式：`allow_merge_commit`、`allow_squash_merge`、`allow_rebase_merge`。
- 分支保护会拦截：必需审批、必需状态检查、要求线性历史、禁止某合并方式等，GitHub 返回 405 并带说明。
- 合并不可撤销，只能事后 revert。
- 合并动作在 GitHub 上记在登录者名下（`merged_by`），与现有评论/批准一致。

### 5.2 合并选项接口

```
GET /api/approvals/{n}/merge-options
```

```json
{
  "canMerge": true,
  "reason": null,
  "methods": ["merge", "squash"],
  "defaultMethod": "merge",
  "draft": false,
  "mergeable": true,
  "mergeableState": "clean",
  "headSha": "…",
  "baseRef": "main",
  "headRef": "topic/x",
  "permissions": { "push": true, "maintain": false, "admin": false }
}
```

- 使用**登录者令牌**取 `GET /repos/{o}/{r}` 的 `permissions` 与三种 `allow_*`，并用 `GET /pulls/{n}` 取 `draft` / `mergeable` / `mergeable_state`。
- 该响应含用户权限，**不能**放进按仓库共享的 `apiCache`；v1 不缓存，或按 `repo + login + PR + headSha` 缓存 60 秒。
- `mergeable` 可能为 `null`（GitHub 异步计算），前端显示“正在计算”，不据此硬禁用。

### 5.3 合并接口

```
POST /api/approvals/{n}/merge
Content-Type: application/json

{ "sha": "<headSha>", "method": "merge|squash|rebase",
  "commitTitle": null, "commitMessage": null }
```

服务端顺序：

1. 会话校验；必须存在 `session.token`（写入令牌）。
2. 校验 body：`sha` 为 40 位十六进制；`method` 在枚举内。
3. 重新取 PR 元信息：已合并 / 已关闭 → 409；`sha !== meta.headSha` → 409。
4. 重新取合并选项：无权限 → 403；draft → 409；方式不被仓库允许 → 400。
5. `mergeable === false` 或 `mergeable_state` 为 `dirty` / `blocked` / `behind` / `unstable` 时返回 409 并附原因；`null` 不拦截，交给 GitHub 判定。
6. 调 GitHub merge；`commit_title` / `commit_message` 为空时不下发，使用仓库默认。
7. 成功或进入合并队列后失效缓存：
   - `repoKey|/api/approvals`
   - `repoKey|/api/approvals/{n}`
   - `repoKey|/diff/{n}`
8. 返回。

成功响应：

```json
{ "ok": true, "merged": true, "sha": "<merge commit sha>",
  "message": "Pull Request successfully merged", "url": "…" }
```

进入合并队列（仓库启用 merge queue 时 GitHub 可能返回 `merged: false`）：

```json
{ "ok": true, "merged": false, "queued": true,
  "message": "Pull request enqueued" }
```

错误映射：

| GitHub 状态 | 返回客户端 | 处理 |
|---|---|---|
| 403 | 403 | 无仓库写权限，或被保护规则拒绝；透传 GitHub message |
| 405 | 409 | 当前不可合并（冲突、缺少审批、检查未过、draft 等）；透传 message |
| 409 | 409 | head 已变化或已合并；提示刷新 |
| 422 | 400 | 参数或合并方式不被接受 |
| 5xx | 502 | `retryable: true` |

### 5.4 前端交互

位置：右侧抽屉，现有 Review 选项下方增加分隔区「合并」。

```
合并
[合并方式 ▾ merge / squash / rebase]
[合并 PR]
main ← topic/x · head abc1234
合并后不可撤销；squash 会丢弃逐提交历史
```

- 仅当 `meta.state === "open" && !meta.merged` 时显示合并区；顺带修正现有只判断 `merged` 的问题（关闭的 PR 也应为只读）。
- 合并按钮禁用条件：无 `canMerge`、draft、`mergeable_state === "dirty"`。`blocked` / `behind` / `unstable` 仍可点击，但按钮下方显示原因，由 GitHub 做最终判定。
- 确认弹窗：
  ```
  确认合并 PR #16？
  main ← topic/x（head abc1234），方式：squash。
  合并后不可撤销，只能 revert。
  ```
- 提交中：按钮禁用，文案「合并中…」。
- 成功：
  - 提示「已合并」，展示 merge commit 短 sha 与链接；
  - 调 `load(n, true, true)` 刷新 meta；
  - 页面转为只读，合并区替换为「已合并」；
  - 列表页缓存由服务端已失效，返回列表时自动重取。
- 进入队列：提示「已加入合并队列」，按钮转为「等待合并」。
- 失败：保留弹窗/抽屉，显示 GitHub 原文；409 时自动刷新 meta 并提示重新确认。
- 把现有「批准合并」改名为「提交批准」，避免和真正的合并按钮混淆（`public/diff.js:1155`）。

## 6. PR 提交浏览

### 6.1 数据源与限制

| 用途 | 接口 | 说明 |
|---|---|---|
| 提交列表 | `GET /pulls/{n}/commits?per_page=100&page=` | 只有 sha / message / author / date / parents / html_url；**没有** stats/files |
| 单提交详情 | `GET /commits/{sha}?per_page=100&page=` | 有 `stats` 和 `files[]`（含 patch、previous_filename）；超过 300 文件时用 Link 头分页，上限 3000 |
| 文件正文 | `GET /contents/{path}?ref=<sha>` | 现有 `getFileText` 直接复用 |

语义边界：

- PR「全部改动」是 merge-base…head（三点）；单提交是 parent…commit（两点），两者不保证逐项相加等于总 Diff。
- 合并过 base 的 merge commit 会出现在提交列表里，其 diff 是相对第一父提交；界面需标「合并提交」。
- 大文件/二进制没有 patch，沿用现有「文件过大」提示。

### 6.2 提交列表接口

```
GET /api/approvals/{n}/commits
```

```json
{
  "items": [{
    "sha": "…",
    "shortSha": "abc1234",
    "headline": "fix: 补充 CSV 表头说明",
    "message": "fix: 补充 CSV 表头说明\n\n…",
    "author": "alice",
    "authorName": "Alice",
    "date": "2026-11-09T…",
    "parents": ["…"],
    "isMerge": false,
    "url": "https://github.com/…/commit/…"
  }],
  "truncated": false,
  "source": "github"
}
```

- 按 GitHub 顺序（旧 → 新）返回；`message` 截断到 8 KB。
- 100 条/页，最多 10 页（1000 条），超出 `truncated: true`。
- 缓存 key：`/commits/{n}/{headSha}`，TTL 5 分钟。新 push 产生新 headSha 时自动使用新 key，无需显式失效。
- 列表接口不带 stats；选择器不展示每提交 +/−，选中后由详情展示。

### 6.3 提交详情接口

```
GET /api/approvals/{n}/commits/{sha}
```

```json
{
  "sha": "…",
  "headline": "…",
  "message": "…",
  "author": "alice",
  "date": "…",
  "parents": ["…"],
  "isMerge": false,
  "stats": { "additions": 12, "deletions": 4, "total": 16 },
  "files": [/* DiffFile[]，与 PR 文件结构一致 */],
  "truncated": false,
  "source": "github"
}
```

- 校验 sha 属于该 PR：用缓存的提交列表做前缀/全量匹配，不满足返回 404。
- 文件分页循环到不足 100 条，最多 30 页（3000 文件）；触顶 `truncated: true`。
- 抽出 `toDiffFile(raw)` 供 `getPrFiles` 与 `getCommitDetail` 共用（`src/diff.ts:156-168`）。
- 缓存 key：`/commit/{n}/{fullSha}`，TTL 30 分钟（sha 不可变）。

### 6.4 提交文件正文接口

```
GET /api/approvals/{n}/commits/{sha}/file?path=<path>&side=base|head
```

返回与现有 `/file` 一致：

```json
{ "path": "docs/a.md", "ref": "<parentSha|sha>", "side": "base|head",
  "text": "…", "truncated": false }
```

规则：

- `side = head`：ref = 提交 sha；文件状态为 `removed` 时返回空正文。
- `side = base`：ref = 第一父提交 sha；无父提交或文件状态为 `added` 时返回空正文；`renamed` 时取 `previousPath`。
- 只允许提交详情里出现的 path，避免借接口读任意文件。
- 复用 `getFileText` 的 30 分钟 `path@ref` 缓存与 400 KB 截断。

### 6.5 前端状态与缓存隔离

现有实现默认「一个 PR 只有一个 head/base」，切提交时必须隔离，否则会复用错正文：

| 位置 | 现状 | 改动 |
|---|---|---|
| `D.texts[path]`（`public/diff.js:8`） | 只按 path | 改为 `D.texts[D.revKey][path]`，或切视图时整体清空 |
| `cachedModel`（`public/diff.js:659`） | key 用 `D.meta.headSha` | key 改用 `D.revKey` |
| 预加载（`public/diff.js:2187`） | 无条件预取全部 PR 文件 | 拆成 `prefetchAll()` / `prefetchCommit()`，只预取当前视图文件 |
| `commentsByPath`（`public/diff.js:2172`） | 全 PR 评论 | 提交视图按 `originalCommitId === sha` 重建 |

实现建议：

- `load()` 只负责取 `/diff` 并保存 `D.all`；全部改动视图的预取移出 `load()`。
- `selectCommit(sha)`：清空当前视图缓存 → 取详情 → 设置 `D.files` → 选中同名文件或第一个文件 → 预取该提交文件 → `render()` → 同步 URL。
- `selectAll()`：从 `D.all` 恢复；若 `/diff` 已过期，用户可手动刷新。

### 6.6 URL 与深链

```
/pr/16/blob/docs/a.md?commit=<sha>&mode=split#L120
/pr/16/blob/docs/a.md                        全部改动（现状）
```

- `public/route.js` 的 `parse` / `build` 增加 `commit`；只接受 7–40 位十六进制，非法值忽略。
- `public/diff.js:176 routeState` 带上当前 `commit`。
- `applyRoute`（`public/diff.js:2349`）增加分支：commit 变化时切换视图，不整页重载。
- `#L` 表示**当前视图版本**的行号；切提交时清空行号，避免同一 `#L120` 指向不同内容。
- 直接打开带 `commit` 的深链：先取 `/diff` 拿 meta，再取提交详情；提交不存在时回退到全部改动并提示。

### 6.7 界面

**选择器**：顶栏标题区（`public/index.html:150` 的 `.wb-title-block`）放一个下拉：

```
[全部改动 · 6585dec..72a8b81]
[abc1234 · fix: 补充 CSV 表头说明]
[def5678 · docs: 更新台账说明]
```

- 选项 `title` 展示作者与时间；提交过多时只渲染前 100 条并附「在 GitHub 查看全部」。
- 选中提交后：

```
历史提交 abc1234 · fix: 补充 CSV 表头说明            [只读]
Alice · 11-09 14:20 · 父提交 def5678 · 3 个文件 +12/−4
[在 GitHub 查看提交] [回到全部改动]
```

- 文件树只显示该提交的文件；标题副行改显示提交 stats。
- 四个视图按钮、主题、表格样式、变更标记全部保留；章节树按当前文件的提交版本重建。
- 进度「已审 x/y」在提交视图隐藏，或改为「本提交 N 个文件」。
- 空提交显示「本次提交没有文件变更」；merge commit 在横幅标注「合并提交」。
- 若当前提交不是 head：横幅提示「该提交不是当前 head」，提供刷新到最新提交的入口。

**只读约束**：

- 隐藏行号「+」、划词评论入口、草稿提交面板。
- 抽屉保留「本提交的评论」列表（只读，带 GitHub 链接）；`originalCommitId === sha` 的评论才展示。
- 草稿仍属于 PR head；提交视图不显示提交按钮，并提示「草稿需回到全部改动视图提交」。
- 不新增评论，不做历史行号 → head 行号的映射。

**已有评论**：`getReviewComments` 补 `commitId`、`originalCommitId`（`src/diff.ts:236-246` 目前丢弃）。提交视图只筛选创建在该提交上的评论；`line` 为空的 outdated 评论只进抽屉列表，不做行内锚定。

### 6.8 合并方式对提交浏览的影响

- **merge commit / rebase merge**：逐提交历史保留，合并后仍可按提交浏览。
- **squash merge**：逐提交历史在目标分支上消失；PR 数据仍在，但提交浏览只剩合并前价值。
- 合并弹窗在选择 `squash` 时明确提示这一点；不在本方案中改变仓库策略。

## 7. 权限与安全

- 读取接口沿用 `dataToken`（服务端只读令牌优先，否则登录者令牌）。
- 合并必须使用 `session.token`，与现有写评论一致；服务端不保存也不使用合并专用令牌。
- `/merge-options` 含用户权限，不做跨用户共享缓存。
- 合并前服务端重新校验 state / head / 权限 / 方式，客户端状态只作展示。
- 沿用现有同源 Cookie + JSON 请求模式；不新增跨域入口。
- 不在日志、响应或页面输出令牌。
- 合并记录以 GitHub 的 `merged_by` 为准，本工具不另建审计表。

## 8. 缓存、性能与限制

- 缓存 key 汇总：

| Key | TTL | 失效 |
|---|---|---|
| `repo|/diff/{n}` | 5 分钟 | 合并、刷新 meta、写评论 |
| `repo|/commits/{n}/{headSha}` | 5 分钟 | 新 head 自动换 key |
| `repo|/commit/{n}/{sha}` | 30 分钟 | sha 不可变，无需失效 |
| `repo|/api/approvals`、`/api/approvals/{n}` | 5 分钟 | 合并后删除 |
| `fileTextCache path@ref` | 30 分钟 | ref 不可变，无需失效 |

- `apiCache` 目前只判断 TTL、从不清理过期项（`src/index.ts:55`）。新增提交 key 前加上限（建议 300 条，写入时删最旧）。
- 提交浏览只取「列表 + 被选中的详情 + 当前文件的正文」，不预取所有提交详情。
- 单提交详情可能很大（文件多、patch 多）；沿用 30 页上限，超出标 `truncated`，页面提示到 GitHub 查看完整 diff。
- 合并本身只增加 2–3 次 GitHub 请求，成本可忽略。

## 9. 边界与异常

| 场景 | 行为 |
|---|---|
| PR 已合并 / 已关闭 | 合并区隐藏；提交浏览仍可用 |
| draft PR | 合并禁用，提示「草稿 PR 不能合并」 |
| 无合并权限 | 合并禁用，提示需要 write/maintain/admin |
| 冲突 / 缺少审批 / 检查未过 | 展示 `mergeable_state` 原因；点击后由 GitHub 405 原文兜底 |
| `mergeable` 为 null | 显示「GitHub 正在计算」，允许尝试合并 |
| 合并期间 head 变化 | GitHub 409；提示刷新并重新确认 |
| 重复合并 | 409 / 已合并状态；刷新页面 |
| 仓库使用 merge queue | 处理 `merged: false` + `queued: true`，提示等待 |
| force push / rebase | 旧提交 sha 可能失效；深链 404 时回退全部改动并提示 |
| 提交视图打开后 head 前进 | 保持当前提交只读，提示「非最新 head」，可一键刷新 |
| 空提交 | 显示「没有文件变更」 |
| merge commit | 标「合并提交」，diff 相对第一父提交 |
| 大文件 / 二进制 | 沿用现有「文件过大」提示 |
| 文件在该提交中新增/删除/改名 | 按该提交的 status 与 previousPath 处理 |
| 提交超过 1000 条 | 列表 `truncated`，提供 GitHub 链接 |
| 提交超过 3000 文件 | 详情 `truncated`，提示到 GitHub 查看 |

## 10. Mock 与演示

- `GET /commits`：为每个 mock PR 合成 **1 个提交**：`sha = meta.headSha`、`parent = meta.baseSha`、`files = PR files`、`stats = meta additions/deletions`、标题「演示提交：PR 全部改动」。

## 14. 验收标准

- 合并按钮仅在 open、非 draft、有权限时可用；不可用原因可见。
- 合并请求带 head sha 锁定；head 变化时不会误合，返回 409。
- 合并成功后页面立即转只读，列表与详情缓存失效，刷新后状态正确。
- 提交选择器能列出 PR 提交；切换后文件树、正文、四种视图、行号锚点均按该提交版本渲染。
- 提交视图为只读，无法新增/提交评论；草稿提示清晰。
- 深链 `?commit=<sha>` 可打开并恢复到指定文件/行。
- force push 后旧提交深链给出明确回退提示，不出现空白页。
- `npm run build`、`npm test` 全绿；mock 模式可完整演示两项能力。
