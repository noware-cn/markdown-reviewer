## 1. 问题与意图

评审一份 Markdown 方案文档时，审阅者要回答的是"这篇文档变成什么样了、我认不认"，而不是"哪几行改了"。当前实现提供了四种视图：阅读改动、前后对照（`sidebyside`）、统一 Diff（`unified`）、分栏 Diff（`split`）。后三种回答的是后者；真正被使用的是阅读视图。

阅读视图现在的毛病集中在同一处：改动状态靠一条**独立坐标尺**（`.drail`）表达。它必须先把每个块在页面上的位置量出来，再画一条与内容分离的竖线；而块高度由渲染决定（标题、表格、代码块的一行占高完全不同），测量时机又受图片加载、表格横向滚动、评论面板开合影响。历史实现曾按行号比例估算，`1ea07d2` 已改为读取 `getBoundingClientRect()` 的像素值——**比例问题修好了，机制问题没有**：改动状态被表达在一条与内容分离的坐标轴上，任何布局变化都要重测一次，且永远存在"线在这里、块在那里"的缝隙。

意图：把"改动"从"独立坐标尺"里搬出来，改成**长在内容上**的标记——块级竖线 + 行内插入/删除标记，并让改动、评论、草稿、已阅在同一条右栏里汇合。数据侧从"行 patch 拼装"升级为"块 AST 对齐 + 行内差异"，从而能可靠处理表格、嵌套列表、段落搬移。

## 2. 目标 / 非目标 / 反目标

**目标**

1. 阅读视图是唯一的文档消费界面；改动标记与文字同流，不存在坐标投射。
2. 块级对齐覆盖表格行、列表项、引用块、代码块，不再只有段落级。
3. 行内标记同时标插入与删除，冲突可判定（同一句里重复词不出歧义）。
4. 改动、评论线程、本地草稿、"已阅"在一条右栏内按文档顺序排列。
5. 提供"最终 / 原始 / 标记"三态显示；三态不改变标记语义，只改变可见性。
6. 中文文档优先：CJK 分词、全角标点、中文数字与计量单位不得被切碎。

**非目标**

- 不做编辑器：仍不能改动仓库文件，没有"接受修订"写回。
- 不做跨文件 diff，不做三次比较（merge base 之外的祖先）。
- 不实现语义级（NLP）判断，如"这句话意思变了吗"。
- 不保留"并排 / 统一"两种视图作为可选模式。

**反目标（即使技术上可行也判为失败）**

- 任何依赖"测量 DOM 高度再把标记投射到另一条坐标轴"的实现。
- 为三种显示状态各写一套渲染路径（状态必须只是可见性开关）。
- 用词级标记覆盖结构性变化（列表变表格、段落变标题），造成"满篇小高亮"。
- 行内标记影响评论锚点（评论必须仍锚在行号上，见 §7.8）。

## 4. 对标项目：能借什么，不能借什么

### 4.1 prosediff

- **事实【文档级】**：Python 工具（`uv` 安装），把两份文档或两个版本渲染成一份静态 HTML 报告；段落对段落排版，词级高亮落在句中；行号槽以 `− + ~ → ←` 等**符号**标增删改与搬移，不依赖颜色；可切换段落/句子视图；支持 Word、LibreOffice、Markdown；许可证 MIT。
- **可借**：① 用符号而非只有颜色做状态编码（打印、色觉障碍可用）；② "段落级配对 + 句中词级"的两层结构；③ 搬移检测的产物形态（`moved to L12`）。
- **不能借**：它是**报告生成器**，不产出可嵌入组件，也没有"评论线程"这一层；Python 运行时进不了 Worker。【推断，依据是文档描述的形态与安装方式】
- **对我们的意义**：证明"段落配对 + 句中高亮 + 符号化行号槽"这一组合在真实文档上可用；它没有解决的问题（评论与改动同栏）恰是我们必须解决的。

### 4.2 Quoin

- **事实【核实】**：`2389-research/Quoin` 是 **Swift 编写的 macOS 原生 WYSIWYG Markdown 编辑器**，许可证 MIT，自述"zero JavaScript"，"local-only"，用 **CriticMarkup 字节**承载建议、评论与修订，另有原生公式与图表。
- **可借**：**CriticMarkup 语法**（`{++增++}`、`{--删--}`、`{~~旧~>新~~}`、`{>>注<<}`）作为"作者在源文件里写建议"的载体。这是公开规范，与本项目将来是否支持"作者提交建议"无关，但我们若做，应采用同一语法以免自造方言。
- **不能借**：任何代码。Swift + SwiftUI，且明确零 JS。
- **对我们的意义**：说明"评审意见写进文档本身"是可行路线，但它是**编辑期**方案；我们的场景是**审阅期**（作者已提交 PR），两者互补而非替代。【推断】

### 4.3 `@atlaskit/editor-plugin-show-diff`

- **事实【核实】**（npm registry）：许可证 Apache-2.0；解包 2.36 MB；依赖含 `prosemirror-changeset`、`@atlaskit/adf-schema`、`@atlaskit/editor-prosemirror` 以及 10 余个 `editor-plugin-*`；peer 依赖 React 18/19 与 `@atlaskit/editor-common`。
- **事实【文档级】**：其 smart diff 设计文档明确否定"全词级"与"全块级"两种极端，按改动密度自适应选择粒度：几个词用词级、一句里改得多整句标、一段里改得多整段标、结构变化（段落→标题、列表→表格）整块替换。
- **可借**：**四档粒度分类器**的思路（我们重写为纯函数，见 §7.5）。
- **不能借**：包本身。它要求 ProseMirror 文档与事务 step，我们的数据是 GitHub 行级 patch；接入等于把渲染层改成 ADF 编辑器。【推断，依据是依赖与 peer 要求】

### 4.4 Vanilla Breeze（设计主张，非代码）

- **事实【文档级】**：其 diff 展示决策页主张"不要做通用 diff viewer"，拆成"行内变更集（带最终/原始/标记切换）"与"评论面"两种形态，并认为并排对照很少值得占横向空间。
- **【未验证】** 是否开源、许可证、是否有可复用组件：我只读了文档页，没有找到代码出处。**不作为技术选型依据。**

### 4.5 其他参照（弱证据，仅作方向确认）

- Word 修订的四个部件：行内标记（插入下划线/删除删除线）、页边批注框、审阅窗格、显示模式（Simple / All Markup / No Markup / Original）。**【文档级】**，来自产品对比文章，非官方规范。
- Google Docs 建议模式：建议行内彩色/删除线 + 评论右栏。**【文档级】**，同上。
- ProseMirror 社区关于"两份文档怎么可视化差异"的讨论：结论收敛为"先对齐块，再只在纯文本块内做行内 diff，其他节点退回块级替换"。**【文档级】，社区讨论，权威性弱。**

### 4.6 实测：`diff-match-patch` 能不能直接用（【核实】）

`npm i diff-match-patch`（1.0.5，Apache-2.0，解包 97,445 B），用 `diff_main` + `diff_cleanupSemantic` 跑三例：

```
重复词：样本覆盖 84 家机构，口径与去年一致[+，样本需补充来源+]。
整句改写：2024 年区域银行智能研发投入同比增长 1[-2.3-][+8.6+]%，其中股份制银行占 42%。[+费用口径未变。+]
词序调整：[- - 专业子方案\n+]- 支撑两条路线的产品研究\n[+ - 专业子方案\n+]
```

结论（三条，都要写进设计）：

1. **消除歧义**：同一段出现两次"样本"，diff 给出的是正确位置；我们现在的"按 needle 顺序查找"在同一段只能放弃标注。
2. **中文数字会被切碎**：`1[-2.3-][+8.6+]` 读起来像改了个字。需要在 token 化与后处理上补工（§7.4）。
3. **搬移不会自动出现**：列表换序显示成一删一增。搬移检测要单独实现（§7.3）。

复现：`mkdir -p /tmp/dmp && cd /tmp/dmp && npm i diff-match-patch`，脚本见附录 A。

## 5. 原理

### 5.1 三层分离：对齐 / 差异 / 呈现

任何文档 diff 都是三件事：**哪些块对应哪些块**（对齐）、**对应的块之间改了什么**（差异）、**怎么画出来**（呈现）。三者混在一起的实现，会在"呈现"里做本该属于"对齐"的判断——本仓库当前的 `wrapAddedText` 就是：它在渲染后的 HTML 里找新增行的文本，用查找顺序代替对齐结果，遇到重复词只能放弃。分层的判据很简单：**差异层只接受两份纯文本并产出区间；呈现层只接受区间并插标签。** 【本设计的核心约束，属判断】

### 5.2 块对齐是地基

行内差异需要"同一块的旧文与新文"。这份配对来自块对齐；对齐错了，行内越精细越错。因此：

- 对齐必须**保序**（non-crossing）：人改文档不会把第 3 段搬到第 5 段前面还指望算法理解。
- 相似度用 **CJK 友好的 2-gram Jaccard**，不用分词器（中文没有空格，Jaccard 在 2-gram 上稳定且无需词典）。
- 只有**同 kind** 才配对（heading↔heading、paragraph↔paragraph、table↔table），跨 kind 一律视为"删一块 + 加一块"，由粒度分类器判为节点级替换。

### 5.3 只在安全文本块内做行内差异

| 块类型 | 行内差异 | 理由 |
| --- | --- | --- |
| 段落、标题、引用、列表项文本 | 做 | 纯文本投影稳定，行内标记语义清晰 |
| 表格单元格 | 做（单元格内） | 行粒度对齐已能确定单元格 |
| 代码块、原始 HTML | 不做，块级标记 | 语法高亮、缩进、转义会让文本投影失真 |
| 图片、分隔线 | 不做，块级标记 | 无可 diff 的文本 |

**降级规则**：安全块内若 token 数 > 5000，退回块级标记。这条是性能护栏，不是质量妥协。

### 5.4 四档粒度

改动密度决定标记粒度（阈值见 §7.5，属**我的决定**，可用语料调）：

1. **词级**：改动用词表达（`12.3%` → `18.6%`）。
2. **句级**：整句改写但块保持同类，标整句而非满句碎高亮。
3. **段级**：块内大半改变，上下两段对照（旧段删除线、新段下划线），不做行内。
4. **节点级**：结构变化（列表变表格、段落变标题）。对齐阶段**不跨 kind 配对**（§7.3），因此结构变化在数据上就是"删一块 + 加一块"；节点级是渲染侧对这对相邻 `removed`/`added` 的呈现方式，不是分类器的输入条件。

设计上只允许**相邻档位**之间跳变；不允许"词级标记覆盖结构变化"，那正是 Atlassian 文档批评的失效模式。

### 5.5 标记与文字同流

CSS 层面只有两种承载：块的 `border-left`（或行内 `::before` 符号）与文本内的 `<ins>` / `<del>`。**任何把标记投射到独立坐标轴上的实现都不允许出现**——无论它按行号比例算，还是按 `getBoundingClientRect()` 量出像素再写 `top/height`。这条是对当前 `.drail` + `syncRail()` 的直接否定，也是本设计删除它们的理由。

### 5.6 冗余编码

状态不能只靠颜色：`+`（插入，绿）/ `−`（删除，红，删除线）/ `~`（修改，青）/ `↔`（搬移，灰）同时出现在块左符号位与行内标记的 `::before`；`aria-label` 与朗读文案给完整句子（"第 12 行，新增一段"）。

### 5.7 显示模式与标记正交

"最终 / 原始 / 标记"只控制可见性：最终态隐藏全部标记（评论仍在右栏），原始态以 base 渲染正文、隐藏插入内容，标记态即完整视图。三态共用同一份渲染产物，仅切换 CSS class 与两个 `hidden` 属性。**禁止**为三态各写一套 HTML 生成。

## 7. 设计

### 7.1 管线

```
base 文本 ─┐
           ├─► parseBlocks() ─► alignBlocks() ─► diffBlock() ─► classify() ─► Decorated[]
head 文本 ─┘                     (LCS+Jaccard)   (dmp on text)   (四档)          │
                                                                                ▼
                                             render(Decorated[], view) ─► HTML + textNode 映射
```

五个纯函数：`parseBlocks`、`alignBlocks`、`diffBlock`、`classify`、`render`。前三者不接触 DOM 与网络，可用 `node --test` 直接覆盖（现有测试基础设施无需扩展）。

### 7.2 块 AST 模型

```ts
type BlockKind = "heading" | "paragraph" | "quote" | "listItem" | "table" | "tableRow" | "code" | "html" | "image" | "hr";
type BlockState = "normal" | "added" | "removed" | "modified" | "moved";

interface Block {
  id: string;              // `${side}:${kind}:${startLine}`，稳定、可复算，容器与其首个子块不冲突
  side: "base" | "head";
  kind: BlockKind;
  level?: number;          // 标题级别 / 列表深度
  parentId?: string;       // 容器块（table / list）的 id；顶层块为空
  children?: Block[];      // 容器内的行/项；渲染时合成一个 <table>/<ul>
  cells?: Cell[];          // 仅 tableRow：按对齐后列序的单元格
  startLine: number;       // 1-based，指向源码行
  endLine: number;
  raw: string;             // 源码原文（含 markdown 标记）
  text: string;            // 纯文本投影（行内标记已剥离）；容器块为其子块拼接
  sig: Sig;                // 对齐特征
}

interface Cell {
  col: number;             // 对齐后的列序（见 §7.3 列对齐）
  text: string;            // 单元格纯文本投影
  raw: string;
}

interface Sig {
  kindTxt: string;         // kind + level（不同级标题不配对）
  norm: string;            // 折叠空白、去 markdown 标点后的文本
  grams: Set<string>;      // CJK 2-gram
  keys: string[];          // 数字/标识符/英文词，用于锚定（patience 阶段）
}
```

**构建方式**：`marked.lexer(raw)` 走 token 树（仓库已在用，见 §3），按 `token.raw` 的换行数累计 `startLine/endLine`；`list`、`table` 展开到 `listItem`、`tableRow` 二级，不再深入。**表格行**与**列表项**进入对齐序列——这是与现状最重要的差别：现状的块模型只有顶层块，列表项与表格行虽然已有逐行 DOM 锚点（`listItemRanges`、`data-line` 属性），但没有进入对齐与差异。

**容器与子块**：`table`、`list` 只作为渲染容器，不参与对齐；对齐与差异在子块上进行，容器只聚合子块状态（任一子块有改动则容器标"有改动"）。块数上限按子块计，容器不额外计数。

**纯文本投影**：`text` 由 `token.tokens` 递归取 `text` 字段拼接，`strong/em/link/code` 只保留其文本内容；`image` 保留 `alt`。投影必须可逆：`text` 只用于 diff，`raw` 用于渲染。

### 7.3 对齐算法

三级策略，逐级降级：

1. **锚定（patience）**：在两份块序列里找 `sig.norm` **唯一且两侧都唯一**的块，作为锚点把序列切段。中文长文档里，标题与含数字的句子大多唯一。
2. **段内配对**：每个切段内，同 `kindTxt` 的块两两算相似度，取 `sim = |A∩B| / |A∪B|`（2-gram Jaccard）；`sim ≥ 0.45` 视为候选，用 **LCS**（DP，段内长度上限 400，超出改贪心）求保序最大配对。
3. **搬移检测**：对齐后，未配对的 `removed` 块 R 与 `added` 块 A 若 `sim ≥ 0.80` 且不破坏保序，标记为一对 `moved`（渲染为"移自 L12"），不参与行内差异。

阈值 0.45 / 0.80 是**我的决定**，依据是"同段微改通常保留一半以上 2-gram"【推断，需在 P0 语料上校准】。

**表格列对齐**：`tableRow` 配对后，行内差异以**单元格**为单位，而不是整行文本：

1. 表头行（首行）配对成功时，按表头文本做列对齐（同样的 Jaccard + 保序 LCS）；列数变化时，未对齐的列整体标"新增列 / 删除列"。
2. 表头无法配对时，退化为按列序直接对应（列序相同即同列）。
3. 每对同列单元格各自跑 §7.4 的行内差异，区间落在**该单元格文本**的偏移上（`unit = ${rowId}#c${col}`）。
4. 行本身未配对（新增行 / 删除行）则不进入单元格差异，整行标记。

这样"加一列"不会染红整张表，也不会把相邻列的内容当成同列改动。

**未配对块的继承**：`added` 块没有 base 侧文本，`removed` 块没有 head 侧文本；它们的 `state` 直接定案，不进入 `diffBlock`。

### 7.4 行内差异

输入：`(baseText, headText)`，均为纯文本投影。输出：`Range[]`，坐标落在 **headText 的字符偏移**上（删除区间用 `[start, end)` 的零宽锚点 + `delText` 负载表达）。

**token 化**（自实现，约 40 行，必须覆盖中文）：

| 类别 | 规则 | 例 |
| --- | --- | --- |
| CJK 汉字 | 每字一 token | `银`、`行` |
| CJK 标点 | 每符号一 token | `，`、`。` |
| 拉丁词 | 连续 `[A-Za-z]+` | `PR`、`Markdown` |
| 数字 | `\d+(\.\d+)?` **连同其后紧跟的 `%`、单位（万/亿/元/家/个/人/次/天/年/月）与前一 `¥`/`$`** 作为一个 token | `18.6%`、`400KB` |
| 空白 | 折叠为单 token | — |
| 其他 | 单符号 | `/`、`-` |

数字连同单位成 token，直接消除 §4.6 的 `1[-2.3-][+8.6+]` 问题：`12.3%` → `18.6%` 会成为一个替换对。

**diff**：`diff_main(base, head, false)` + `diff_cleanupSemanticLossless`，**在 token 序列上做**（把 token 用不可见分隔符连接后 diff，再按 token 边界还原）。

**后处理（三条，必须实现）**：

1. 相邻同类区间合并，间隔 ≤ 2 个 token 时合并（避免"改了三个地方"其实是改写一句话）。
2. 删除区间两侧各扩 1 个 token 若为标点（`，`、`的`），使标记读起来完整。
3. 区间端点吸附到词边界（CJK 按字边界，拉丁按词边界），不得从词中间开始。

**不变量**：把 `headText` 按输出区间施加后必须**逐字节等于** `headText`；删除区间携带的 `delText` 必须能在 `baseText` 中**该块起点之后**原样找回（断言存在，不断言唯一）。token 序列以 `\u0001` 连接后送入 diff；若还原出的 op 序列拼不回 token 列表，该块降级为块级标记。这条用属性测试守（§9）。

### 7.5 粒度分类

```
r = 变更 token 数 / head 侧 token 数      // 仅对已配对的同 kind 块计算
r ≤ 0.15            → inline   （词级）
0.15 < r ≤ 0.60     → sentence （句级：按句切分，整句标）
r > 0.60            → block    （段级：旧段删除线 + 新段下划线）
未配对（新增 / 删除 / 结构变化）→ node（节点级：整块替换）
```

句子切分：`[。！？；\n]` 为界（中文文档可靠）；英文按 `. ! ?` + 空格。句级标记的视觉形态是"句内不再细分"。

阈值与档位映射均为**我的决定**；P0 语料上允许调整，调整需同步更新测试期望。

### 7.6 渲染契约

`Decorated` 是渲染层唯一输入：

```ts
interface Decorated {
  block: Block;                       // head 侧；removed 块为 base 侧
  state: BlockState;
  inline?: Array<{          // 扁平条目：每条自带 unit/op/start/end（实现计划 T7 与此一致）
    op: "ins" | "del";
    unit: string;                     // block.id，或 tableRow 的 `${block.id}#c${col}`
    start: number; end: number;       // unit 文本内的字符偏移
    delText?: string;                 // del 区间携带的原文
  }>;
  baseText?: string;                  // segment / node 档的旧文本
  pair?: { blockId: string; line: number };  // moved：内容来自/去向
  children?: Decorated[];             // 容器块的行/项
}
```

渲染步骤：块 HTML 生成时，同时返回**文本节点映射表** `[{textStart, textEnd, htmlStart, htmlEnd}]`（按 `unit` 分组）；把 `inline` 区间按 `textStart` 换算成 `htmlStart`，在 HTML 字符串里插入 `<ins class="md-ins">` / `<del class="md-del">`。**沿用既有类名 `.md-ins`**（现有多处 CSS 与 5 处测试断言依赖它），只新增 `.md-del`。**在字符串层投影，不依赖 DOM TreeWalker**——这条直接适配现有极简 DOM stub 的测试环境【核实：`test/generation.test.mjs` 的 stub 只有 `querySelector` 等极少方法】。

**DOM 契约（不得删改）**：每个块必须继续输出 `class="md-block"`、`data-line`、`data-end-line`、`data-block`，原文块另有 `data-base-line`、`data-side="RIGHT"`，行锚点 `.line-anchor`，有评论时 `.has-comments`；新增 `data-block-id` 供引擎与右栏互相定位。`applyAnchor`、章节联动、评论映射、CSV 视图都依赖这套属性，改名即回归。

删除块（`removed`、`node` 档的旧块）渲染在对应新增块之前或之后，取决于同一容器内的顺序，保持"旧上、新下"。`moved` 块只在卡片与符号位标注，正文不插行内标记。

## 9. 测试策略

1. **黄金语料**（P0 产出）：JSON 描述 `{base, head, expect: {blocks: [...], states, granularity, inline}}`。每个用例覆盖一类真实改动（数字微调、整句改写、列表换序、表格加行、标题升降级、段内搬移）。

## 附录 B 实现细节的落定（供写代码的人直接用）

这些是评审过程中发现的"不应留给你决定、也不该由实现者临场发明"的点，已按最保守方式定下：

| 项 | 结论 |
| --- | --- |
| 新文件注册 | 新增 `public/semdiff.js`（引擎 + vendored dmp，IIFE 包装），在 `public/index.html` 与 `public/doc.html` 中于 `diff.js` **之前**引入，版本号参数随其余资源一并递增；若它需要在登录后访问，需同步加入 `wrangler.jsonc` 的 `run_worker_first` |
| 三态控件载体 | 复用现有 `#wbMarks` 复选框的位置与样式，改为三态分段控件；`.marks-off` 保留为内部类，`1/2/3` 快捷键映射到三态 |
| 搬移计数 | 一对 `moved` 计 1 处改动；卡片文案"移自 L12"；不参与 `+n −m` 行数统计 |
| 行内 diff 清理函数 | 用 `diff_cleanupSemanticLossless`（§4.6 的实验用的是 `diff_cleanupSemantic`，仅用于演示，不作为实现依据） |
| 分隔符 | token 序列以 `\u0001` 连接；还原不一致即降级 |
| 章节色条 | 保留 `.cbar`，计数由 `Decorated[]` 供给 |
| 空/异常输入 | `base` 或 `head` 为空时不做对齐，全部按 `added` / `removed` 呈现 |
| 引用文档 | 无 base 侧输入，直接 `render` 且 `inline: []` |

## 附录 C 术语

- **块**：一个可独立对齐的 Markdown 结构单元（标题、段落、列表项、表格行、代码块…）。
- **安全文本块**：允许做行内差异的块类型集合（§5.3）。
- **decorations**：差异层输出、渲染层消费的标记数据，不含任何坐标。
- **锚定（patience）**：用两侧唯一的块先切开序列，再做段内配对。
- **搬移**：同一内容从一处挪到另一处，语义上是"移动"而非"删+加"。
